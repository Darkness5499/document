
## 1. Cách kết nối với Spring Boot

Để kết nối Spring Boot với MongoDB, chúng ta sử dụng hệ sinh thái **Spring Data MongoDB**.

### Bước 1: Thêm Dependency

Thêm starter vào file `pom.xml` (Maven):

XML

```
<dependency>
    <groupId>https://www.springframework.org/boot</groupId>
    <artifactId>spring-boot-starter-data-mongodb</artifactId>
</dependency>

```

### Bước 2: Cấu hình Connection String

Khai báo thông tin kết nối trong file `application.yml`:

YAML

```
spring:
  data:
    mongodb:
      uri: mongodb://username:password@localhost:27017/my_database

```

### Bước 3: Định nghĩa Entity (Document) và Repository

Sử dụng các annotation của Spring Data Mongo để map đối tượng Java thành Document:

Java

```
@Document(collection = "users") // Xác định tên Collection
public class User {
    @Id
    private String id; // MongoDB mặc định dùng kiểu ObjectId (String hoặc BigInteger)
    
    @Indexed(unique = true) // Tạo Index đơn và đảm bảo duy nhất
    private String email;
    
    private String name;
    private List<String> roles; // Khả năng lưu mảng tự nhiên trong NoSQL
    
    // Getters, Setters, Constructors
}

```

Tạo lớp Interface để thao tác dữ liệu:

Java

```
@Repository
public interface UserRepository extends MongoRepository<User, String> {
    // Tự động sinh câu lệnh dựa trên tên hàm (Query Method)
    Optional<User> findByEmail(String email); 
}

```

### Các kiểu dữ liệu phổ biến (BSON Types)

MongoDB sử dụng định dạng **BSON** (Binary JSON) mở rộng từ JSON để lưu trữ, hỗ trợ các kiểu dữ liệu:

-   **String:** Chuỗi văn bản UTF-8 (Ví dụ: tên, email).

-   **ObjectId:** Chuỗi 12-byte tự động sinh ra cho trường `_id`, chứa mốc thời gian (timestamp) giúp tăng tiến tuần tự và không bị trùng lặp trên toàn cụm hệ thống.

-   **Boolean:** Giá trị `true` / `false`.

-   **Integer/Long:** Số nguyên 32-bit hoặc 64-bit (Dùng lưu số lượng, ID).

-   **Double / Decimal128:** Số thập phân. _Lưu ý: Khi tính tiền, bắt buộc dùng kiểu `Decimal128` để tránh sai số._

-   **Array:** Mảng chứa nhiều phần tử (Ví dụ: `["admin", "user"]`).

-   **Object (Embedded Document):** Một tài liệu JSON nhỏ lồng bên trong một tài liệu lớn.

-   **Date:** Lưu trữ thời gian dưới dạng Unix epoch (UTC).


## 3. Các Use Cases (Trường hợp áp dụng lý tưởng)

MongoDB phát huy sức mạnh tối đa trong các bài toán:

-   **Hệ thống E-Commerce (Giỏ hàng & Sản phẩm):** Mỗi loại sản phẩm (quần áo, điện tử, gia dụng) có các thuộc tính hoàn toàn khác nhau. Tính chất _Schemaless_ giúp lưu tất cả vào một Collection `products` mà không cần thiết kế hàng chục bảng phụ.

-   **Quản lý Nội dung (CMS, Blog, Báo chí):** Bài viết có danh mục, danh sách thẻ (tags), danh sách bình luận (comments). Tất cả được _Embed (nhúng)_ gọn gàng vào 1 Document bài viết, giúp tốc độ đọc trang chủ cực nhanh.

-   **Hồ sơ người dùng (User Profiles) & Cấu hình (Settings):** Lưu trữ thông tin tùy biến, cấu hình động thay đổi liên tục của người dùng.

-   **Lưu trữ dữ liệu Log hoặc IoT bán cấu trúc:** Dữ liệu đẩy về có cấu trúc không đồng nhất và cần tốc độ ghi cao.


## 4. Kiến trúc & Cách tối ưu tốc độ (Performance Tuning)

### Kiến trúc hệ thống mở rộng

MongoDB cung cấp hai mô hình kiến trúc chính thức để vận hành lớn:

1.  **Replica Set (Tính sẵn sàng cao - High Availability):** Gồm 1 nút **Primary** (nhận lệnh Đọc/Ghi) và các nút **Secondary** (chỉ Đọc và đồng bộ dữ liệu tự động). Nếu nút Primary sập, cụm tự động bầu chọn (Failover) một nút Secondary lên thay thế trong vài giây.

2.  **Sharded Cluster (Mở rộng chiều ngang - Horizontal Scaling):** Khi dữ liệu quá lớn vượt quá dung lượng RAM/Ổ đĩa của một máy, dữ liệu sẽ được phân tán (sharding) ra nhiều máy dựa trên một từ khóa gọi là **Shard Key**.


### Cách tối ưu tốc độ (Performance Tuning)

-   **Quy tắc Index ESR (Equality, Sort, Range):** Khi tạo Compound Index (Index tổ hợp), luôn xếp các trường theo thứ tự: Trường so sánh bằng (`$eq`) → Trường dùng để sắp xếp (`sort`) → Trường so sánh khoảng (`$gt`, `$in`).

-   **Covered Queries:** Thiết kế câu lệnh sao cho toàn bộ các trường cần lấy ra nằm trọn trong Index. MongoDB sẽ trả kết quả ngay từ RAM chứa Index mà không cần tốn chi phí đọc dữ liệu gốc từ ổ đĩa.

-   **Sử dụng `.explain("executionStats")`:** Luôn kiểm tra câu lệnh truy vấn. Tối ưu sao cho chỉ số `totalDocsExamined` tiệm cận với `nReturned`, và trạng thái phải là `IXSCAN` (quét Index) thay vì `COLLSCAN` (quét toàn bộ bảng).

-   **Tối ưu hóa RAM (WiredTiger Cache):** MongoDB sử dụng bộ máy lưu trữ WiredTiger. Hãy đảm bảo kích thước RAM của server đủ lớn để chứa toàn bộ các Index (Index Working Set) trên bộ nhớ đệm.


## 5. Các lưu ý quan trọng khi dùng (Caveats)

-   **Giới hạn kích thước Document 16MB:** Một Document đơn lẻ (bao gồm tất cả các mảng và object lồng bên trong) không được vượt quá 16MB. Nếu thiết kế mảng phình to vô hạn, hệ thống chắc chắn sẽ bị crash.

-   **Đánh đổi tính toàn vẹn (No Foreign Keys):** MongoDB không có cơ chế ràng buộc khóa ngoại (Foreign Key Constraint) ở tầng DB. Việc đảm bảo tính nhất quán dữ liệu giữa các Collection phụ thuộc hoàn toàn vào code ở tầng Application (Spring Boot) của bạn.

-   **Hạn chế lạm dụng `$lookup` (JOIN):** Phép `$lookup` trong NoSQL cực kỳ tốn tài nguyên và làm chậm hệ thống. Hãy ưu tiên tư duy phi chuẩn hóa (chấp nhận lưu trùng lặp dữ liệu) để hạn chế tối đa việc phải nối các Collection.

-   **Mặc định không có Transaction đa tài liệu:** Mặc dù hỗ trợ Multi-Document Transactions từ bản 4.0, nhưng nó đi kèm chi phí hiệu năng rất cao. Bạn chỉ nên dùng khi thực sự cần thiết (như giao dịch tiền tệ), còn lại hãy thiết kế dữ liệu hội tụ về một Document duy nhất để tận dụng tính nguyên tử (Atomicity) mặc định trên một Document.


## 6. Các Problems và Solutions phổ biến trong thực tế

### Problem 1: Unbounded Array (Mảng phình to vô hạn)

-   _Tình huống:_ Bạn thiết kế Collection `User` và tạo một trường `private List<String> friendIds` để lưu danh sách bạn bè theo kiểu _Embedding_. Với các tài khoản KOL có hàng triệu bạn bè, Document sẽ vượt quá giới hạn 16MB.

-   _Solution:_ Chuyển sang chiến lược **Referencing** kết hợp phân trang. Tách riêng ra một Collection `friendships`, mỗi document chỉ lưu cặp quan hệ đơn giản: `{ user_id: 1, friend_id: 2 }`.


### Problem 2: Đọc dữ liệu cũ trên nút Secondary (Stale Data)

-   _Tình huống:_ Hệ thống chạy mô hình Replica Set. Luồng A vừa cập nhật số dư tài khoản trên nút Primary. Ngay lập tức, Luồng B thực hiện đọc số dư nhưng Spring Boot lại điều hướng request đọc sang nút Secondary. Do dữ liệu chưa kịp đồng bộ xong bất đồng bộ, Luồng B đọc phải giá trị cũ.

-   _Solution:_ Cấu hình **Read Concern** và **Read Preference** trong Spring Boot. Với các tác vụ nhạy cảm cần dữ liệu mới nhất, cấu hình `readPreference=primary` để ép hệ thống đọc trực tiếp từ nút Primary.


### Problem 3: Viết câu lệnh Aggregation quá chậm khi hệ thống lớn

-   _Tình huống:_ Bạn dùng Stage `$lookup` để JOIN hai tập hợp khổng lồ `orders` và `users`, hệ thống bị treo hoặc phản hồi mất vài giây.

-   _Solution:_ Áp dụng tư duy **Denormalization (Phi chuẩn hóa)**. Thay vì chỉ lưu `userId` trong Collection `orders`, hãy chủ động lưu trùng lặp một vài thông tin ít thay đổi như `userName`, `userEmail` vào thẳng trong Document `order` tại thời điểm mua hàng. Việc này giúp loại bỏ hoàn toàn lệnh `$lookup` khi hiển thị danh sách đơn hàng.


### Problem 4: Câu lệnh `.sort()` bị lỗi hụt bộ nhớ (In-Memory Sort Limit)

-   _Tình huống:_ Bạn chạy một câu lệnh tìm kiếm và sắp xếp trên tập dữ liệu lớn không được đánh Index, hệ thống bắn lỗi: `Executor error during find command ... Sort exceeded memory limit of 33554432 bytes`.

-   _Solution:_ MongoDB giới hạn việc sắp xếp dữ liệu trên RAM không được quá 32MB nếu không có Index. Cách xử lý triệt để là **tạo một Compound Index** chứa cả trường tìm kiếm và trường sắp xếp theo đúng quy tắc ESR để MongoDB sắp xếp dữ liệu ngay trên cấu trúc cây của Index.
